# 性能分析：为什么移动、编辑都不如 Figma 顺滑

## 1. 结论

卡顿的根本原因不是某个操作写得慢，而是 **每一次鼠标移动或数据修改，整个画布（以及侧边栏）都会被 React 完整地重新渲染一遍**。图表越大，每一帧的耗时越长。

Figma 用 WebGL 自己绘制画布，只重画屏幕上看得见、并且真正变化了的部分；drawDB 每张表都是 SVG 里嵌入的 HTML（`foreignObject`），并且没有做任何"只渲染变化部分"的优化。

---

## 2. 实测数据

测试图表：80 张表 × 每表 8 个字段，79 条关系线（在内置浏览器中临时创建，不影响你的数据）。

每次操作从触发到主线程处理完的耗时（20 次的平均值）。作为参照，空任务的基准耗时约 9ms。流畅需要每帧 ≤ 16ms。

| 操作                           | 每帧耗时（平均） | 每帧耗时（p90） |
| ------------------------------ | ---------------- | --------------- |
| 鼠标在画布上移动（什么都不按） | **约 178ms**     | 234ms           |
| 空格 + 拖动平移                | **约 198ms**     | 242ms           |
| 滚轮平移                       | **约 223ms**     | 277ms           |
| 拖动一张表                     | **约 253ms**     | 295ms           |
| 在侧边栏输入表名（每按一个键） | **约 261ms**     | 308ms           |

开发模式和正式构建版（`vite preview`）的结果几乎一样，说明瓶颈不在开发模式的额外开销。

### 渲染次数（临时加计数器统计，已删除）

| 操作                        | 表格组件渲染次数 | 关系线组件渲染次数 |
| --------------------------- | ---------------- | ------------------ |
| 鼠标移动 1 次（什么都不按） | **80**（全部）   | **79**（全部）     |
| 鼠标移动 10 次              | 800              | 790                |
| 空格平移 10 帧              | 880              | 869                |

## 3. 原因（按影响从大到小）

### ① 鼠标坐标存在 React state 里 ——影响最大

- 位置：`src/context/CanvasContext.jsx` 中的 `detectPointerMovement` → `setPointerScreenCoords`
- 画布上**每一次** `pointermove` 都会更新这个 state，`Canvas` 组件随之重新渲染；而 `Canvas` 下面的所有表格、关系线、注释、区域都没有做缓存，于是全部跟着重新渲染。
- 结果是：鼠标只是从画布上划过，什么都没做，也会卡。

### ② 画布元素没有缓存（`React.memo`），回调每次都是新函数

- 位置：`src/components/EditorCanvas/Canvas.jsx` 渲染 `<Table>`、`<Relationship>`、`<Note>`、`<Area>` 的地方
- `Table`、`Relationship` 等组件没有用 `React.memo`；传入的 `onPointerDown={() => {...}}` 每次渲染都是新函数。
- 所以哪怕只拖动一张表，其他 79 张没有变化的表也会全部重新渲染。

### ③ 每个字段都包着一个 Semi `Popover`

- 位置：`src/components/EditorCanvas/Table.jsx` 中 `settings.showFieldSummary ? <Popover ...>`
- 「字段摘要」默认是开启的（`showFieldSummary: true`），80 张表 × 8 个字段 = **640 个 Popover 组件**。每次重新渲染都要处理一遍，开销很大。

### ④ 拖动或编辑时，侧边栏和「问题」面板也会整体重新计算

- 拖动表格时，每一帧都会调用 `updateTable` → `tables` 数组变化 → 所有用到 `tables` 的组件都会重新渲染，包括：
  - **侧边栏表格列表**（`TablesTab.jsx`）：80 个折叠面板，加上拖拽排序组件。
  - **「问题」面板**（`Issues.jsx`）：每当 `tables` 变化就执行一次 `getIssues()`，**对整个图表做一遍校验**。拖动的每一帧、输入的每一个字，都要做一次全图校验。
- 这也是在侧边栏输入表名时，每按一个键要 200ms 以上的原因。

### ⑤ 平移和拖动没有按「帧」合并

- 鼠标事件的频率可能比屏幕刷新率高（游戏鼠标可以达到每秒 500–1000 次），但每一个事件都会立刻触发一次 `setTransform` 或 `updateTable`，进而导致一次完整渲染。
- 应该用 `requestAnimationFrame` 合并，一帧最多更新一次。

### ⑥ 浏览器绘制本身的开销（与 React 无关）

- **没有视口裁剪**：屏幕外看不见的表格也照样渲染、照样绘制。
- **`foreignObject`**：SVG 里嵌入的 HTML，排版和绘制成本比纯 SVG 高很多。
- **`drop-shadow-lg`**：每张表都加了 CSS 阴影滤镜（`Table.jsx`、`View.jsx`）。滤镜在平移时需要重新计算，表格越多越慢。

### ⑦ 平移时反复保存（第 4 次修改中已修复）

- 平移时，每一帧都可能触发一次完整的 IndexedDB 写入。详见 `docs/changelog.md` 的「第 4 次」。

## 4. 上游的相关工作

上游有一个尚未合并的 PR：[drawdb-io/drawdb#1122](https://github.com/drawdb-io/drawdb/pull/1122)「Improve large diagram scalability with viewport virtualization」，覆盖了上面的 ②⑤⑥ 以及侧边栏虚拟化：

- 只渲染视口内的元素（视口裁剪，配合空间索引）
- 表格和关系线组件使用 `memo`
- 用 `requestAnimationFrame` 合并平移和缩放
- 侧边栏列表虚拟化，「问题」检测改为基于索引的算法

改动量很大（新增 1531 行，删除 363 行，涉及 29 个文件），和你 fork 上已有的修改会有不少冲突。没有涉及 ①（鼠标坐标的 state）。

## 5. 优化方案（建议的先后顺序）

| 步骤 | 内容                                                                                        | 预期效果                                     | 改动量 |
| ---- | ------------------------------------------------------------------------------------------- | -------------------------------------------- | ------ |
| 1    | 鼠标坐标改用 ref 保存，只在真正需要时（拖动、连线、框选）才触发渲染                         | 鼠标划过画布时不再卡，**最立竿见影**         | 小～中 |
| 2    | `Table`、`Relationship`、`Note`、`Area` 加上 `React.memo`，回调用 `useCallback` 或改为传 id | 拖动一张表时只重新渲染这一张，其余 79 张不动 | 中     |
| 3    | 平移、拖动用 `requestAnimationFrame` 合并，每帧最多更新一次                                 | 高频鼠标下更稳定                             | 小     |
| 4    | 「问题」检测改为防抖（停止操作约 300ms 后再算），侧边栏列表项加 `memo`                      | 拖动和输入时不再每帧做全图校验               | 小     |
| 5    | 字段 Popover 改为鼠标悬停时才创建                                                           | 减少 640 个常驻组件                          | 小～中 |
| 6    | 视口裁剪：只渲染屏幕内的元素（可以参考或拆用 #1122）                                        | 大图表的根本解决办法                         | 大     |
| 7    | 去掉或简化 `drop-shadow-lg`                                                                 | 减少平移时的绘制开销                         | 很小   |

步骤 1～4 改动可控、风险低，预计就能让中等规模（几十张表）的图表明显顺滑；步骤 6 是上百张表时的根本解决办法。

每完成一步，都可以用同一个 80 张表的测试图表重新测量，对比前后数据。
